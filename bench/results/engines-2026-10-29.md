## 속도·자원

| 엔진 | 실행 방식 | 모델 로딩 | 페이지당 | 최대 VRAM |
|---|---|---|---|---|
| PaddleOCR-VL-1.6 | CLI + vLLM 서버(0.22.1) | 94초 | 2.8초 | 14.8GB (vLLM 50% 예약) |
| MinerU 4.0.12 (MinerU2.5-Pro-1.2B) | api-server(vLLM 0.28) + CLI | 188초 | 2.7초 | 측정 실패 |
| OvisOCR2 | vLLM 0.22.1 오프라인 | 191초 | 2.1초 | 18.1GB (vLLM 80% 예약) |

- 페이지당 시간에는 문서별 CLI 실행 비용(1~2초)이 섞여 있어 실제 서비스(서버 상주)에서는 더 빠르다. 그림 많은 논문(en_paper_figs)은 세 엔진 모두 가장 느림 (18~40초/3쪽).
- VRAM은 vLLM이 미리 잡는 비율에 따라 정해지므로 엔진 간 비교 의미가 작다. 실제 모델은 모두 1~2GB급.
- PaddleOCR 기본(native Paddle) 백엔드는 이 PC에서 GPU 12% / CPU 100%로 3쪽에 10분 넘게 걸려 중단. vLLM 백엔드로만 실용적.

## 품질 (사람이 눈으로 비교한 대표 사례)

| 항목 | PaddleOCR-VL | MinerU | OvisOCR2 |
|---|---|---|---|
| **한국어 스캔** (ko_notes_scan) | 거의 정확. 띄어쓰기 1곳 붙음, `[답안용]`→`【답안】` 1곳 | **원문과 거의 동일** | 오류 다수: `1강`→`1장`, `민족의`→`민族的`, `문예`→`문제`, `신앙`→`신양` |
| 손글씨 수식 (zh_handwritten) | 오타 1(`线性`→`统性`), 첨자 `β_r`→`β_n` | 오타 1(`线性`→`绕性`) | 문장 가장 정확, 단 `α`를 `d`로 읽음 |
| 스캔 수식 (zh_math_scan) | LaTeX 정상 | LaTeX 정상, 가장 촘촘 | LaTeX 정상 |
| 표 | HTML 표 | 마크다운 표 (스캔 DB 교재 표도 인식) | HTML 표 |
| 슬라이드 | 제목·글머리 유지, 장식 기호(☐) 남음 | 장식 기호 제거, 수식은 `\boxed` 블록 | 장식 기호(☐) 남음 |
| 그림 | 이미지 파일로 분리 | base64로 본문에 포함 (용량 큼) | 태그 제거 (본문만) |

## 결론 (제안)

- **주 엔진: MinerU** — 한국어 정확도가 가장 좋고, 표·수식 모두 안정적. 서버 모드(api-server)가 이미 있어 워커 연결이 쉽다. 단 라이선스상 **사용 사실 표시 의무**가 있으므로 사이트에 표기 필요. 그림 base64는 워커에서 제거하거나 브라우저 정리기가 처리.
- 보조 후보: OvisOCR2 — 가장 빠르고 손글씨에 강하지만 한국어에서 한자 섞임 오류가 있어 한국어 문서에는 부적합.
- PaddleOCR-VL — 품질은 중간이지만 Python API 멈춤 문제와 vLLM을 다른 venv에서 빌려 써야 하는 구성 때문에 운영 부담이 가장 크다.

한계: 한국어 문서가 필기 노트 1종(스캔은 흉내)뿐이다. 실제 한국어 교과서·스캔본으로 한 번 더 확인하면 좋다.
