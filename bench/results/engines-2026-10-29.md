## 속도·자원

| 엔진 | 실행 방식 | 모델 로딩 | 페이지당 | 최대 VRAM |
|---|---|---|---|---|
| PaddleOCR-VL-1.6 | CLI + vLLM 서버(0.22.1) | 94초 | 2.8초 | 14.8GB (vLLM 50% 예약) |
| MinerU 4.0.12 (MinerU2.5-Pro-1.2B) | api-server(vLLM 0.28) + CLI | 188초 | 2.7초 | 측정 실패 |
| OvisOCR2 | vLLM 0.22.1 오프라인 | 191초 | 2.1초 | 18.1GB (vLLM 80% 예약) |

- 페이지당 시간에는 문서별 CLI 실행 비용(1~2초)이 섞여 있어 실제 서비스(서버 상주)에서는 더 빠르다. 그림 많은 논문(en_paper_figs)은 세 엔진 모두 가장 느림 (18~40초/3쪽).
- VRAM은 vLLM이 미리 잡는 비율에 따라 정해지므로 엔진 간 비교 의미가 작다. 실제 모델은 모두 1~2GB급.
- PaddleOCR 기본(native Paddle) 백엔드는 이 PC에서 GPU 12% / CPU 100%로 3쪽에 10분 넘게 걸려 중단. vLLM 백엔드로만 실용적.

## 품질 (사람이 눈으로 비교한 대표 사례)

| 항목 | PaddleOCR-VL | MinerU | OvisOCR2 |
|---|---|---|---|
| **한국어 스캔** (ko_notes_scan) | 거의 정확. 띄어쓰기 1곳 붙음, `[답안용]`→`【답안】` 1곳 | **원문과 거의 동일** | 오류 다수: `1강`→`1장`, `민족의`→`민族的`, `문예`→`문제`, `신앙`→`신양` |
| 손글씨 수식 (zh_handwritten) | 오타 1(`线性`→`统性`), 첨자 `β_r`→`β_n` | 오타 1(`线性`→`绕性`) | 문장 가장 정확, 단 `α`를 `d`로 읽음 |
| 스캔 수식 (zh_math_scan) | LaTeX 정상 | LaTeX 정상, 가장 촘촘 | LaTeX 정상 |

| 그림 | 이미지 파일로 분리 | base64로 본문에 포함 (용량 큼) | 태그 제거 (본문만) |

## 토큰 (벤치마크 A, o200k_base)

`npm run tokens` (결과 `2026-10-29T05-08-47-tokens.json`). 엔진 출력은 `bench/baselines/<엔진>/`에 넣고, 실제 서비스처럼 `output.js` 정리기를 거친 값(`+opt`)으로 비교. `mineru`는 base64 그림을 뺀 것(6단계 워커가 할 처리), `mineru-img`는 그대로.

| 문서 묶음 | 브라우저 mdbeaver | Paddle+opt | MinerU+opt | Ovis+opt | MinerU (그림 포함) |
|---|---|---|---|---|---|
| 텍스트 레이어 있는 7개 | **9,199** | 10,228 | 10,730 | 10,455 | 620,175 |
| 스캔·손글씨 4개 | 47 (거의 못 읽음) | **10,078** | 10,237 | 10,413 | 127,000 |

- **엔진끼리 토큰 차이는 5% 이내** → 토큰은 엔진 선택 기준이 못 된다. 정확도(C)가 결정한다.
- 텍스트 PDF에서 GPU 엔진이 브라우저보다 11~17% 많은데, 대부분 **시험지 수식**(234 → 850~1,070) 때문: 수식이 텍스트 레이어에 없어 브라우저는 빠뜨리고 엔진은 LaTeX로 살린 것. 수식 문서를 빼면 차이는 5~8%.
- 스캔본은 브라우저로는 내용이 없다(47토큰). GPU 엔진이 필요한 이유가 숫자로 확인됨.
- **MinerU base64 그림은 58배**(10.7천 → 62만 토큰). 워커에서 반드시 제거.
- 토큰이 적다고 좋은 게 아니다: 한국어 노트에서 Paddle·Ovis가 브라우저보다 적은 건 일부 글자를 빠뜨리거나 틀렸기 때문. "토큰당 정확도"는 C단계에서 확인.

## PDF를 AI에 그대로 넣을 때 vs md로 바꿔 넣을 때 (Claude, 추정)

Claude 공식 문서(PDF support, Vision): PDF는 **추출 텍스트 + 페이지마다 이미지**로 과금. 이미지 = ⌈가로/28⌉×⌈세로/28⌉ 토큰, 페이지당 상한 1,568(표준) ~ 4,784(Claude 4.7 이후 고해상도). 페이지를 몇 픽셀로 렌더링하는지는 문서에 없어 두 상한으로 범위를 냄. 텍스트는 o200k로 셈(Claude 토크나이저와 다름 → 근사).

| | 31쪽 합계 토큰 |
|---|---|
| PDF 그대로 | **약 6만 ~ 16만** (텍스트 1.2만 + 이미지 4.9만~14.8만) |
| MinerU md (+opt) | **약 2.1만** |
| 절감 | **약 3 ~ 7.6배** |

- 문서별로는 슬라이드 8~22배, 텍스트 논문·교과서 3~15배, 스캔 2~9배.
- 손글씨(zh_handwritten)만 0.8~2.4배: 손글씨 수식을 LaTeX로 길게 옮기기 때문.
- 근거 확인: 공식 문서의 Bedrock 예시 "3쪽 PDF ≈ 7,000토큰"(≈ 2,300/쪽)은 위 범위의 아래쪽과 맞음.
- 정확한 값은 `count_tokens` API(무료)로 PDF 블록과 md를 같은 모델에 넣어 재면 된다 — API 키 필요.

## 결론 (제안)

- **주 엔진: MinerU** — 한국어 정확도가 가장 좋고, 표·수식 모두 안정적. 서버 모드(api-server)가 이미 있어 워커 연결이 쉽다. 단 라이선스상 **사용 사실 표시 의무**가 있으므로 사이트에 표기 필요. 그림 base64는 워커에서 제거하거나 브라우저 정리기가 처리.
- 보조 후보: OvisOCR2 — 가장 빠르고 손글씨에 강하지만 한국어에서 한자 섞임 오류가 있어 한국어 문서에는 부적합.
- PaddleOCR-VL — 품질은 중간이지만 Python API 멈춤 문제와 vLLM을 다른 venv에서 빌려 써야 하는 구성 때문에 운영 부담이 가장 크다.

한계: 한국어 문서가 필기 노트 1종(스캔은 흉내)뿐이다. 실제 한국어 교과서·스캔본으로 한 번 더 확인하면 좋다.
